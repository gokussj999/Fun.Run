## Executive Decision

**Selected strategy:** **`prisma migrate diff` baseline squash**

Generate one initial baseline migration from `schema.prisma` using `prisma migrate diff --from-empty`, then **remove** the orphan `20260710000000_add_pending_tx` migration by folding its objects into the baseline.

| Option | Verdict | Reason |
|--------|---------|--------|
| **A. `migrate diff` → baseline squash** | ✅ **Selected** | Matches `schema.prisma` exactly; fixes CI; single auditable history |
| B. Manual SQL baseline (no diff) | ❌ Rejected | High FK/index ordering risk; duplicates Prisma tooling |
| C. Keep `add_pending_tx` as migration #2 | ❌ Rejected | Empty DB fails — base tables missing before `pending_txs` |
| D. `db push` only (no migrate history) | ❌ Rejected | CI and production use `migrate deploy`; not versioned |

## Environment Handling

### A. Fresh database (CI, Docker, new Neon branch)

```bash
pnpm --filter @funrun/database db:migrate
```

Applies `20260709000000_baseline` → full schema.

### B. Database created via `db push` (schema already matches)

If tables exist and match `schema.prisma`, **do not** run destructive migrate. Baseline the history:

```bash
# 1. Verify schema matches (optional)
npx prisma migrate diff \
  --from-url "$DATABASE_URL" \
  --to-schema-datamodel prisma/schema.prisma \
  --exit-code

# exit 0 = schemas match → safe to baseline

# 2. Mark baseline as applied without re-running SQL
npx prisma migrate resolve --applied 20260709000000_baseline
```

### C. Database with only `add_pending_tx` applied

Rare (only `pending_txs` + `TxStatus` exist). Options:

1. **Preferred:** Neon branch snapshot → drop DB → `migrate deploy` (dev/staging only)
2. **Alternative:** `migrate resolve --applied` baseline + manual `migrate diff` for missing tables (error-prone — avoid in prod)

### D. Legacy `backend/` database (old column names)

Legacy schema (`wallet`, `v_sol`, `run_balance`, etc.) is **not compatible** with platform Prisma models. Migration strategy:

- Platform V2 uses a **new schema** (greenfield or separate Neon database)
- Legacy → platform data migration is a **separate Sprint 5+ ETL** — out of Sprint 1 scope
- Do **not** attempt in-place ALTER from legacy tables to Prisma V2 columns in Task 2

## Rollback

| Scenario | Action |
|----------|--------|
| Task 2 baseline fails on fresh DB | `git revert` migration commit; continue `db push` interim |
| Baseline applied to wrong env | Restore Neon branch / `pg_dump` snapshot taken **before** migrate |
| Applied migration edited by mistake | **Never edit applied migrations** — add forward-fix migration instead |
| Need interim off-chain trading | Unaffected — Task 1 is docs-only; legacy path unchanged |

**Pre-migrate checklist (production/staging):**

1. Neon branch or `pg_dump` backup
2. Run `node scripts/migration-inventory.mjs` and archive JSON output
3. Confirm `DATABASE_URL` points to intended environment
